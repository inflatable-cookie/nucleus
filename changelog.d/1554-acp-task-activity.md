- ACP task threads now render the task's real activity with native `plan`, `tool_call` and `tool_call_update` updates derived from `taskActivity`: the plan tracks Queued → Working → Review → Merge → Close, each participant run and automatic repair has its own call with a plain title and a current detail line, and a task with no live run still shows its current wait, so a review gap or a person-owned wait is never hidden. Each wait occurrence has its own call lifetime, keyed by the fact the activity reading names as its owner (a decision, stop, host wait, permission, repair episode or the last concluded run), so a wait keeps one call while it lasts, a secondary stop never splits a continuing host wait, two separate decisions never share one completed call, an owner key that returns after its call ended opens a new call rather than reviving the settled one (settled history keeps one quiet call per run and per repair), and a wait that recurs after work started still updates. A launch the host is still answering is its own wait, and so is each deferred read of the coordinator's host. Repairs are attempt-scoped: each attempt keeps one call id from reservation through bind to its own settlement, is never completed just because a reading hides it, and never reopens. Each attempt ends from one settlement fact for that exact attempt: a bound attempt from its own run, and a reservation that ends before any run is bound (an escalation, an admission or capacity wait, a resolve, a clear or a newer episode) from one recorded settlement event, whichever path ended it. A retry under the same episode is a new call that an earlier attempt's history can never settle or hide, a launch recorded before launches named their episode keeps its own cause and outage charge rule, a settled attempt never returns to in progress, and the displayed attempt is derived from settled charge facts, so a launch refunded after a proved pre-send host-read refusal stays out of the count. Messages stay for what a person reads — a verdict summary, an operator question and the finish — with no raw IDs, SHAs or host identifiers; a question names its decision in plain words and points at the Nucleus Inbox, which is where it is answered. A client without structured updates appends exactly one status line per real change and none on a tick that changed nothing (Spec 068 batch 2).

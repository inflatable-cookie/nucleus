Every delivered message now carries its own reply route, so a recipient can answer the sender without any thread registering itself. Nucleus issues one opaque, service-bound reply handle per message, bound to the sender's identity as the sending ticket or host verification proved it, and the delivered text carries the exact `Reply: nucleus tell {to:{reply:"<handle>"}}` line instead of the old "use the tell route your session names" hint. `tell` accepts `{reply}` in `to` and delivers through the ordinary path (queued for a busy recipient, steered into a live turn, unknown outcomes recorded and never resent); `ask` accepts it too when the sender is a project planner or named project agent. A handle reaches exactly the sender of that one message, works only for that message's recipient, expires seven days after issue, and means nothing beyond delivering a message there. A reply is an ordinary message, so it carries its own handle and a conversation continues both ways. An archived or gone sender refuses the reply with that fact and is never revived. A thread that is none of Nucleus's addressable roles — such as a T3 design thread writing to a project — can now be answered.

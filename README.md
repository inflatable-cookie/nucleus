# Nucleus

Trusted local Paseo 0.8 plugin. Durable task queue, isolated worktree dispatch, independent PR review, mechanical merge gates, GitHub merge, local main sync, and coordinator closeout. Includes pause/drain, subscription pools, task history, and concurrency limits.

The plugin is installed as `nucleus`. Open **Nucleus** in the Paseo sidebar. New installations start paused with an empty worker pool. The task list defaults to **Open**, hiding done and cancelled tasks; **All** includes retained completed history. Clicking a task opens its detail in a scrollable modal while the list remains full-width.

## Install

The first release, **0.1.0**, is prepared for **macOS on Apple silicon**. These
commands become available when the public GitHub Release is published.

If you already have Nucleus:

```sh
nucleus install inflatable-cookie/nucleus@v0.1.0
nucleus version
```

On a machine without `nucleus`, download and unpack the standalone package. It
includes Node; no npm install or source checkout is needed.

```sh
bootstrap_dir=$(mktemp -d)
curl --fail --location --proto '=https' --proto-redir '=https' \
  https://github.com/inflatable-cookie/nucleus/releases/download/v0.1.0/nucleus-0.1.0-darwin-arm64.tar.gz \
  -o "$bootstrap_dir/nucleus.tar.gz"
tar -xzf "$bootstrap_dir/nucleus.tar.gz" -C "$bootstrap_dir"
"$bootstrap_dir/runtime/node" "$bootstrap_dir/bin/nucleus.mjs" install inflatable-cookie/nucleus@v0.1.0
export PATH="$HOME/.local/bin:$PATH"
nucleus version
nucleus data-home
```

The installer downloads through the release manifest and checks its SHA-256 and
package inventory before activation. Add `~/.local/bin` to your shell's PATH
for future sessions. Keep the bootstrap directory until installation succeeds.
Nucleus stores its data in `~/.nucleus` (`NUCLEUS_DATA_HOME` overrides it).

For Paseo, run `nucleus integrate paseo` to register the installed package, then
reload the `nucleus` plugin in Paseo. Fresh installations start paused; configure
profiles and limits in Settings before resuming. Release installs stay pinned;
the local main channel is opt-in. See the [release contract](docs/knowledge/contracts/release.md)
for preparation, proof and publishing steps.

## Operator controls

- **Pause and drain** immediately prevents new dispatch and follow-up processing. Already issued operations may finish; running workers are not interrupted. Submissions, callbacks, and observed worker states continue to be stored. Resume reconciles stored results before admitting more work.
- **Paused · managed workers are idle** means all known plugin threads have recent idle/error/closed observations and no uncertain creation remains. It does not cover unrelated threads, workspace scripts, or other applications. Paused state survives plugin reload and app/daemon restart.
- **Dispatch limits** defaults each project to **5 concurrent tasks**. The separate global cap defaults to **32**, with a maximum of **64**. The per-project cap allows 1–32 and applies equally to every project; project overrides set one project's own slot limit. Both caps count task slots; the scheduler skips full projects. **Concurrent Paseo daemon calls** default to **6** and are bounded 1–32, like the stall threshold and the hold and lane-drain timers. Concurrently spawned processes (Git and hooks) share a fixed internal bound read at the point of spawn, and long project validation runs as a background execution that never holds a lane. Every bound applies without a restart. All nine of these limits are set in Settings → Dispatch limits, and that is the only route that changes them.
- **Settings-only capacity.** Only Settings → Dispatch limits changes the host's dispatch limits; there is no install, admin rights or document to manage. The CLI and every ordinary agent route refuse plainly — "only the operator changes Nucleus's dispatch limits, in Settings", nothing changed, do not retry — and a repeated call changes nothing. The local board takes the same Settings writes with a live link from `nucleus ui`. Each applied change is recorded durably with its time, the surface it arrived from, and every value before and after; `queue.capacity-state` reads the values in force and that record, and Settings shows the same record. Saving the values already in force is a no-op and records nothing, and a restart, upgrade or service roll keeps both the values and the record. This is accident prevention, not authentication: a same-uid process that deliberately writes the plugin bridge's own frame is not stopped, and the record names that surface without claiming who sent it. The #426 root-owned installer and document artifacts remain in the tree, reviewed and unused, as history; [the service boundary contract](docs/knowledge/contracts/service-boundary.md), "Settings-only capacity writes", owns the rule.
- The worktree admission budget follows the global task-slot limit in **Dispatch Limits** immediately; there is no separate 12-worktree ceiling. Lowering it defers new worktrees and preserves existing ones. Paseo latency backpressure still applies.
- A reservation counts from the first workspace-creation intent through review, revision, merge, sync, and closeout; blocked/error results release it once their thread stops. Uncertain creation and missing callbacks retain capacity. While paused, completed workers retain reservations until resume.
- Nucleus assigns a permanent number per repository. Tasks appear as `#N` within a project or `repo#N` across projects. Submission receipts and operation status include both `number` and `reference`; detail and outcome accept a reference or repository plus number. Worker PR titles start with the bare number (`304: Task title`). UUID task IDs and `ns-<task ID>` branches stay unchanged.
- Nucleus-owned worker workspaces are titled `<State>: <N> <task title>` and follow phase or hold changes, such as `Working: 304 Legacy video triage`. Every state prefix is one word. A trailing `worker` is omitted from the workspace title. Title updates use persisted, idempotent intents and do not rename branches or directories. Review-entry external workspaces retain their existing names.
- The header's navigation tabs are the working views: Tasks, Papercuts and Planning. A multi-project selector in the header scopes every task and planning view; the Pipeline view has its own filter switch to turn project filtering off without clearing the selection (Spec 026). Its right side holds icon-only controls with accessible labels, in this order: Telemetry, Settings, Refresh, and Pause/Resume (Tom, 2026-09-27). Settings is Nucleus's native Paseo settings screen (`addSettingsScreen`, opened by the Settings icon through `openSettings`), holding Profiles, Subscriptions and Dispatch limits (Tom, 2026-09-27).
- A workspace whose project root belongs to a Nucleus project can open the **Nucleus board** tab (or run the Open Nucleus board command). The panel resolves the workspace's project by repository (`project.get`) and shows that project's Pipeline, Lanes and Planning with the selector preset to it; task and lane detail work as on the main surface. A workspace outside every Nucleus project shows a plain message. The Papercuts and Telemetry views stay in the main surface, and the panel shows no operator settings (Spec 026).
- The task surface is a board of open work that fills the available viewport below the header. Pipeline columns are Triage, Attention, Queued, Working, Review and Closing; Triage includes papercut-tagged leads with tag chips and a tag filter. Queued is `queued`, Working is dispatching, working and changes requested, Attention is blocked, error and needs_attention, Review is awaiting review and reviewing, and Closing is verifying, merging, syncing and closing. Each card shows once whatever its lane count; the board has no swim-lane view (Tom, 2026-11-08). Lanes live in Planning. The project dropdown shares the tab row and filters the whole board. A stopped task's card badges the stop category no other badge carries — Incident, Recovery or Stopped run; holds and waits keep their own badges — derived from the same precedence `task.next` reports. Cards open the detail modal and stay free of action buttons, and task movement remains owned by orchestration. The detail modal leads with a **Next** section (Spec 050): the current stop or wait in one plain line, the active run with role, profile and last activity, one button per verb `task.next` reports as available — opening a short form for its required reason or instruction, or a role select and pool profile picker for routing verbs — and greyed buttons for the rest with their refusal on hover. Apply calls `queue.task` with the prefilled args and the operator caller identity, shows the result or refusal inline, and refreshes detail; a merge hold that is the last blocker past `holdEscalationMinutes` shows on the Decisions view as a Nucleus-raised card with Release and Keep (Keep asks for a reason); other Nucleus-raised items stay read-only (Spec 040).
- **Telemetry** separates wall-clock waiting from active lifecycle work. Task detail shows total, waiting, active, current-stage age, exact/partial evidence and stage timing. The aggregate page filters by repository, scope, profile group and time window, then reports p50/p95 stage time, completion rate, intervention rate, hook timing and recovery role/status/cause. Older records are marked partial where exact boundaries were not stored.
- **Profiles** explicitly enables worker, reviewer, and coordinator roles and permitted task scopes. Existing pool entries migrate as worker-only. Reviewers must use a known model different from every observed author model; opaque automatic routes cannot establish independence. Named-profile model, effort, permission mode, and features are preserved. Explicit thinking overrides must be supported. Preferred profiles can allow fallback or be mandatory.
- Profiles sharing a subscription share a group. Weight is a per-model share: the last 50 assignments balance by each model's weighted share first, subscription-group counts pace without deciding, and lifetime totals break ties. This balances assignments, not tokens or measured subscription consumption. When a task names an optional `complexity`, a profile's rated `capability` adds one bounded preference on top of the share: an exact fit doubles the effective weight, the farthest fit halves it, linearly in between; either side unset changes nothing. The preference never gates, never overrides an explicit request, and never starves a mismatched profile.
- **Subscription availability** marks groups unavailable, optionally until an ISO timestamp. Mark available resets eligibility. Nucleus changes automatic availability only when Paseo attributes concrete quota, credit or usage-balance exhaustion to the exact agent assigned through that subscription group. An authenticated `providerUnavailable: true` callback is a hint; Nucleus verifies the assigned agent's observed provider error before failover. A recovery coordinator may report the same exact worker-provider evidence after the worker releases its workspace. Auxiliary CLIs, nested models, reviewers, workspace naming providers, unrelated agents, generic HTTP 429s, network errors and ordinary task blockers cannot disable the assigned group. Other provider failures can still be marked manually. Transient 429 rate limits and 502/503/529 provider errors resume in the retained thread with bounded backoff before Nucleus raises attention; [Spec 016](docs/knowledge/specs/016-live-evidence-before-recovery.md) defines the retry and failover boundary.
- Originating thread is immutable. Coordinator remapping increments an assignment generation. Old coordinator callbacks lose authority immediately; the old thread must stop before its replacement runs. Leave the coordinator blank for automatic role-pool selection.

## Submission

Tasks are submitted by chatterbox threads through the API or local CLI. There is no manual submission form:

```sh
node /absolute/path/to/plugin/bin/queue-cli.mjs submit /absolute/path/to/submission.json
```

```json
{
  "submissionId": "stable-project-card-id",
  "title": "Implement approved handoff",
  "repoPath": "/absolute/real/git/root",
  "baseBranch": "main",
  "planningCommit": "40-character-commit-sha",
  "handoffPath": "docs/handoffs/card.md",
  "originAgentId": "originating-thread-id",
  "coordinatorAgentId": "coordinator-thread-id",
  "scope": "general"
}
```

Optional routing: `scope`, `complexity` (`very_low` to `very_high` or `null`), `preferredProfileId`, `requirePreferred`, `thinkingOptionId`. Every new task runs the responsible lifecycle ([Spec 058](docs/knowledge/specs/058-responsible-tasks.md)); explicit `responsible: false` is refused, and `manualVerification: true` cannot select the old lifecycle. Submissions and pool settings written before the 2026-10-12 rename (task `capability`, pool `capabilities`) still parse; a payload carrying both spellings is refused.

Optional `skipPRReview: true` explicitly requests merge on completion without an independent reviewer. It defaults to false, including existing tasks. A PR and idle worker remain required; all deterministic head, GitHub rules/checks, workspace and integration checks still apply. Coordinator closeout still runs after merge and sync. Nucleus refuses the option when the target repository binds closeout to a required integration-write `task.closeout` hook, because that hook needs an accepted review identity the lane never produces, so the task could merge but never close. The refusal happens during submission and handoff preparation, before any task, workspace or worker exists. This policy is fixed at submission, shown in task detail, and recorded in submission/activity history. Reusing the submission ID with a changed policy is rejected.

Completion notifications are also explicit submission policy. `notifyOriginOnCloseout: true` opts in the origin; `completionNotificationAgentIds` nominates up to 32 live Paseo threads, including threads in other projects. IDs are sorted and deduplicated, resolved to their current workspaces, and fixed in submission identity. Omitted false/empty policy preserves legacy identity and produces no completion notice.

A live thread can join or leave an unfinished task's completion cohort without choosing another identity:

```sh
node bin/nucleus-subscribe.mjs TASK_ID subscribe
node bin/nucleus-subscribe.mjs TASK_ID unsubscribe
```

The helper requires `PASEO_AGENT_ID`. The RPC validates that exact live thread and records its workspace. A thread Nucleus already records as a recipient or subscriber can still unsubscribe while archived or missing, on that recorded workspace binding; adding a subscription, an unrecorded recipient, an unreadable identity or one observed in another workspace refuses with nothing written. Creator seeds and self-service overrides remain separate in task detail. The effective union freezes atomically at `done`; one independently fenced notice is created per recipient. A creator that nominated itself, and the owner's own subscription, are the owner entry and reach whoever owns the task now; any other creator or self entry is delivered to the recorded recipient (Spec 040). Cohort membership grants no task, review, recovery, or escalation authority.

A task has one owner: the thread its attention, completion, hold-release and planning notices reach. Change it from a thread (the board's owner picker was removed with the old lifecycle):

```sh
node bin/nucleus-reparent.mjs NEW_OWNER_AGENT_ID --task TASK_ID [--task TASK_ID ...] --reason TEXT
node bin/nucleus-reparent.mjs NEW_OWNER_AGENT_ID --project PROJECT --from OLD_OWNER_AGENT_ID --reason TEXT
```

The caller (`PASEO_AGENT_ID`) is the project's owner thread or the tasks' current owner; the board acts as the operator. The new owner must be a live planning thread; the old one may be archived or gone. Each task changes in one write, and owner-placed holds, owner notices and the creator's own completion nomination follow without being rewritten. See [Spec 040](docs/knowledge/specs/040-merge-hold-release-prompts.md#one-task-owner).

**Profiles** (Settings) is one page for stored records and their dispatch settings. A row shows the name, On/Off, the model in plain words, and one status only when attention is needed (unavailable, subscription paused, needs a request). **Edit** opens the editor on the same page: provider, model, thinking and mode as dropdowns, then Cost, Capability, Selection and, under Advanced, Subscription, Weight and assignment counts. Explanations sit behind a `?`. Changes save on entry; failures show beside the field, and a brief Saved status appears after a write. **Remove** is at the bottom of the open editor and asks once. A pool entry whose profile is gone appears after the live rows as **This profile is gone**, with Remove on that stale row. If the catalog is empty or the daemon is disconnected, nothing is marked stale. The separate **Subscriptions** tab contains availability controls. Subscription rows expose **Pause** and, when unavailable, **Reset**. Counts come from the rolling 50-assignment window and lifetime totals; neither measures token consumption.

 Reusing a submission ID with the same normalized input returns the existing task; different content is rejected. The handoff must be a regular tracked file committed on the integration branch. Dispatch also requires a clean integration checkout synchronized with origin, if present. The plugin does not overwrite or update a dirty integration checkout.

CLI methods: `backup.now`, `backup.list`, `snapshot`, `detail`, `telemetry`, `submit`, `completion-subscription`, `pool`, `control`, `stop-threads`, `task`, `next`, `availability`, `capacity-state`, `refresh`, `lane.upsert`, `lane.status`, `lanes`, `projects`, `project.upsert`, `project.get`, `project.park`, `project.unpark`, `project.remove`, `project.removal-blockers`, `project.qa.run`, `project.qa.cancel`, `project.qa.dismiss`, `project.qa.get`, `project.qa.list`, `repository.set`, `repository.get`, `repositories`, `repository.rekey-preview`, `repository.rekey`, `repository.rekey-receipt`, `papercut.add`, `papercut.list`, `papercut.get`, `papercut.edit`, `papercut.promote`, `papercut.promote-task`, `papercut.close`, `papercut.set-lanes`, `lead.add`, `lead.edit`, `lead.get`, `lead.version`, `lead.list`, `lead.set-lanes`, `lead.set-tags`, `lead.drop`, `lead.reopen`, `lead.promote`, `lead.check`, `lead.approve`, `lead.promote-task`, `lead.import`, `decision.add`, `decision.get`, `decision.list`, `decision.answer`, `decision.withdraw`, `decision.link`, `decision.supersede`, `lane.document.get`, `lane.document.edit`, `plan.get`, `plans`, `plan.set`, `outcome-search`. Pass the JSON payload on stdin with `-`, for example `node bin/queue-cli.mjs plan.get - <<'JSON'` followed by the JSON and a closing `JSON` line. A heredoc avoids shell quoting and leaves no shared temporary file for a concurrent session to overwrite. A file path still works, and no argument means `{}`. Contracts are in `shared/contracts.ts`. Methods that include a dot are passed through as-is. `stop-threads` (Queue #650) is the operator's stop-every-active-thread control: it refuses unless Nucleus is paused, stops each live managed thread through the durable stop path with a `paused_stop` marker, and unpause resumes every marked thread in its own agent.

`next` (`task.next`) is the read-before-steer call: pass `taskId` or a `reference` such as `owner/name#12`, and it returns the task's phase and reason, the active run (role, agent, profile, status, last activity; an initial worker, which has no run record, reads from its task-row binding with role `worker`), the PR head, the current stop or wait with its reason, owner and evidence, the hold fences, and every registered owner verb with `available`, prefilled `args` and the `refusal` for each that does not apply. It reads the store only — no remote calls. Copy the args of an available verb, add the free-text fields its `fill` list names (a reason or instruction), and call `task`; the CLI fills `caller` from `PASEO_AGENT_ID`, and each control applied that way writes one `owner_control` event recording verb, caller, owner-thread match, reason and phase before and after. `next` lists `route` once for each of `worker`, `reviewer` and `coordinator`, prefilled with that role's current profile. The superseded narrow actions were deleted on 2026-10-15; `set_routing`, `exclude_worker` and `coordinator` remain because no verb expresses them.

**When something is stuck:** read `next`, then use `force: true` with a reason on `retry_effect` or `move`. The project planner, Nucleus planner or operator can force. A forced retry settles the named effect without sending it; a forced move records the blockers it settles. Merge still checks the exact head at GitHub. Without an applied verdict at that head, it needs explicit operator source acceptance and, for a relay, a note quoting Tom. See [Spec 050](docs/knowledge/specs/050-owner-task-controls.md#owners-can-always-get-past-a-failed-gate-tom-2026-11-04).

`route` (Spec 050, step 3) points one role's next run at a named profile on any unfinished task, before or after dispatch. Call `task` with `action: "route"`, the current `taskId` and `version`, `role`, `profileId`, a required `reason`, and optional `thinkingOptionId` and `now`. The profile is recorded on the same `profileRequests` field the selection path already reads, so the next revision or replacement worker, the next reviewer or the next coordinator uses it; submission-time requests stay in history. The same profile is allowed as a runtime reset. Naming a profile a recorded `workerExclusion` covers lifts that exclusion for this task, with the lift recorded and the exclusion history kept. An owner-routed reviewer is used even when it shares the current author's model — the `owner_control` event records the waived independence and the reviewer prompt names every prior author — while automatic selection keeps preferring an independent reviewer and a fresh reviewer agent never reviews its own head. The profile must exist, be enabled for the role and support the thinking option; an unavailable subscription group is refused with its retry time and the eligible alternatives. With `now: true`, an idle or between-runs role switches immediately and a live run gets one durable stop through the existing active-turn cancellation path: the run is superseded and released, then the replacement starts on the new route with the task, workspace, branch, PR and commits kept. A coordinator replacement increments `coordinatorGeneration`. In particular the narrow `coordinator` action, which remaps the task to one `coordinatorAgentId`, is superseded by `route role=coordinator`: `route` clears the recorded agent and advances the generation so the next coordinator is selected from the pool by the routed profile, and the `coordinator` action keeps its own behaviour only to pin one specific existing agent.

`restart` (Spec 050, step 4) gets a stopped, stalled or checkpointed run going again with one call. Call `task` with `action: "restart"`, the current `taskId` and `version`, a required `reason`, and optional `role` (`worker`, `reviewer` or `coordinator`, derived from the phase when omitted: worker or revision in working, changes_requested, blocked, error and pre-PR needs_attention; reviewer in reviewing and awaiting_review; coordinator when one is the active run), `instruction` and `fresh` (default false). Nucleus derives every run, head, checkpoint and identity from the task, settles the incidents, recovery episodes, reminders, carries and checkpoint holds the restart supersedes as superseded (history retained) inside the action's own transaction — a refused restart changes nothing — and starts the next run through the existing internals: a continuation turn on the same agent by default, or a fresh agent on the role's current route when `fresh` is true. Before its run fence, the restart also settles a finished run of another role — completion durably recorded, agent observed idle with no active turn and no pending permission — releasing it through the reconciliation release path, so a completed-but-unreleased recovery run whose coordinator is idle no longer fences the reviewer continuation (#3569); a run without a recorded completion, or whose agent is active, uncertain or unobservable, still fences with a refusal naming the run. A checkpointed same-head reviewer continues on its own run from that checkpoint; `fresh` supersedes it without a verdict and returns to `awaiting_review` at the same head. It covers a blocked or errored pre-PR worker, a revision whose callback went missing, a stalled live turn (which issues the durable `restart` and continues the run once inactivity is observed), an absent worker, reviewer or coordinator creation (restarted under the same run ID after a complete inventory lookup), a pre-dispatch admission park (which returns to `queued` and re-runs admission whatever its attention flag said), and a stopped coordinator resolution. `next` lists `restart` whenever the active or most recent run of a role is stopped, stalled, idle without a result, checkpointed, blocked or errored.

For blocked workers, stopped revisions and retained workers between runs, omitting `fresh` continues the retained agent; `fresh: true` replaces the agent on its current worker route. A stopped reviewer likewise resumes on the retained reviewer agent by default, or on a new agent with `fresh: true`. Both modes retain the workspace, branch and PR. When creation is absent, there is no retained agent to continue: either mode observes inventory and retries creation under the same run ID. Stalled workers and reviewers apply the same agent choice after the durable stop observes inactivity. Coordinator resolution retry does not support `fresh: true` and refuses it before changing state; use `route role=coordinator` with `now` to replace the coordinator agent.

`move` (Spec 050, step 5) sends a task to one step of its own lifecycle with one call: `task` with `action: "move"`, the current `taskId` and `version`, `to` (`work`, `review`, `merge` or `closeout`) and a required `reason` (plus an optional `instruction` for `work`). `next` lists one view per target with prefilled args, or the plain refusal for each that does not apply. A move acts on the phase and the actual runs, never on attention or recovery flags, and settles the fences it supersedes — the open incident, escalated recovery, reminders, carry and checkpoint intent — with history kept, then writes one `owner_control` event; `work`, `review`, `merge` and `closeout` settle inside the move's own transaction (for closeout, inside the accepted merge), so a refused move changes nothing, and `review` first settles a finished run of another role whose agent is observed idle (#3569). `work` returns the task to its author for a revision with the instruction (a gone author is replaced by a fresh one on the worker route; a stopped or checkpointed reviewer lease is superseded first). `review` supersedes accepted credit, answered episodes and a checkpointed reviewer, and starts a fresh reviewer at the verified current PR head (a workerless review-entry task whose PR head changed must use `move to=work` to start a revision worker in its task workspace). `merge` is allowed only with a `ready_to_merge` review at the exact current PR head, re-verified at the forge, and enters the ordinary verification turn — pre-merge hooks and merge gates — so a clean advance of the integration base is not drift and no exact-base equality is checked. Qualified owner acceptance (2026-10-17): `merge` also takes a `qualification` — what the authorized owner accepts over a released published `changes_required` verdict at the exact current head, with any deferred work named. The caller must be the project's owner thread, the operator at the board, or a relayed operator ruling with its recorded note; Nucleus records one durable acceptance (actor, authority, reason, qualification, the bound review and publication identities) beside the untouched verdict and writes an `owner_acceptance` event, and the ordinary verification, pre-merge hooks, `requiredMergeReview` and Nucleus's GitHub review-requirement gate read it in place of reviewer approval. Required checks and hooks still refuse into the ordinary revision loop, merge holds stay real until their holder releases them, a changed head invalidates the acceptance for merge (history kept), and task detail and the outcome show the reviewer verdict and the acceptance side by side. `closeout` is allowed only when the PR is observed merged: it records the external merge, settles the runs and enters ordinary closeout, and never mints a review. Any other target or missing invariant refuses with one plain reason. `revise` and `rereview` folded into `move to=work` and `move to=review` on 2026-10-15, and the last four narrow controls into `restart` and `amend_brief` on 2026-10-19: `restart role=reviewer` continues a checkpointed reviewer, a parked `restart` re-runs the parked step or answers an escalation when nothing else applies, and `amend_brief` with no text re-pins a handoff. The reconcile-and-continue pair (`assess_recovery`/`apply_recovery`), `close_superseded_reviewer_incident` and `preserve_mechanical_review` were deleted on 2026-10-14 (Spec 050 step 4); the verbs own what they did.

`complete` (Spec 050, phase 2) finishes a dispatched task that has no PR to merge — report-only or no-code — on the owner's call: `task` with `action: "complete"`, the current `taskId` and `version`, a required `reason`, and an optional `artifact: {key, version, digest}` naming the exact lane document it accepts. It is refused only by a live run (observed active or holding a permission), an open PR (recorded or on the forge), merge intent, a terminal task, or a task that never dispatched. One transaction releases the finished runs and settles the superseded fences — attention, the open incident, the escalated recovery with its pending action recorded as refused, reminders, carry and checkpoint intent — with history kept, then records a `done` outcome marked `owner_completed` with the reason and artifact. No brief heading is proof of scope.

`retry_effect` (Spec 050, step 5) retries one recorded failed or uncertain side effect: `task` with `action: "retry_effect"`, a required `reason`, and an optional `effect` key copied from `next` — when omitted it acts only if exactly one effect is pending. `next` lists one view per pending effect with its stable key and a one-line summary: a hook occurrence that still holds its transition, an unproven workspace creation, an unconfirmed workspace archive, a failed runtime retirement, a skipped or uncertain build-output cleanup, a merged task's holding retention gate, an unrecorded review publication, a planning base the retained workspace cannot dispatch from, a rebind-displaced workspace still unarchived, and the latest failed advisory hook occurrence. Nucleus observes the remote or local resource first through the existing handler: a found-done effect is bound, a proven-absent one is retried once (including a workspace or agent creation the installed client refused before send), and an unknown outcome refuses with what was observed. An applied retry first settles the fences it obsoletes — a stale incident, escalated recovery, reminders, carry or checkpoint intent — with history kept; a refused retry changes nothing. Discarding unpublished checkout state needs an explicit `discard: true` — `next` lists `discard` among the fields to fill for an occurrence held after checkout disposal. Each applied retry writes one `owner_control` event naming the effect key. The workspace-creation replay inside the registered `retry_validation` verb observes and retries that effect through the same `retry_effect` path. The superseded narrow actions were deleted on 2026-10-15.


`proof` (task 405, [Spec 055](docs/knowledge/specs/055-source-immutable-proof-executor.md)) activates the task's ONE brief-named author-side proof execution, for an external or manual source author without a supported heavy launch route. The brief or handoff must name it structurally — `queue.proofExecution: {selector, inputs?}` — and `next` lists the verb with its reason field or the plain refusal. An existing task whose brief already names it is not recreated: `amend_brief` binds the accepted frontmatter's declaration in the same write, before any reservation, and once the one executor is reserved a change or removal is refused with nothing written while a body-only amendment that keeps the selector and input hashes still lands. `task` with `action: "proof"`, the current `taskId` and `version`, and a required `reason` is accepted only from the operator at the board or through a relayed operator note, on an idle unfinished pre-review task with the exact published PR head, an unspent allowance and no dispatch hold or pause; any other condition refuses and names the ordinary exit. Nucleus creates one genuine proof-only `executor` run on the same task through the normal admission environment, workspace, slot admission, lease and callback credential. It runs only that selector at the exact published head, forbids source writes, commits, pushes, branch swaps, installations, review publication, merges and dispatch, and reports `proof_executed` with `proofResult {status, selector, exitCode, evidence}`; a passing claim is re-proved against the source before it is accepted, and a wrong selector, a missing result or source drift refuses it. The executor's own run, agent, model, selector, inputs and result are recorded in `proofExecutions`, separate from the unchanged source-author declaration, and a later reviewer must be independent of both. A failed, denied, lost or unknown execution spends the same single allowance and is never retried or refunded, and independent review is still required afterwards. Nothing releases a hold: a dispatch hold or pause refuses activation, a merge hold is untouched, and feature delivery activates nothing.

`backup.now` creates a verified snapshot on demand; `backup.list` returns the retained snapshots with time, compressed size, verification and any backup error. Both take `{}` and are available through `node bin/queue-cli.mjs backup.now` and `backup.list`. Nucleus snapshots every 6 hours and before schema migrations. It retains 24 scheduled, 14 daily and 8 weekly snapshots, under the configured checkout placement. Fresh installs use a portable root under the data home. Existing installs adopt their recorded external mount once; an absent or unwritable configured volume is reported (durably, beside the store) and retried without a fallback. Restore with [the runbook](docs/knowledge/operations/restore.md).

Nucleus no longer writes portable-record exports for the separate retired Nucleus system or its contract 009 shadow stream: both producers are retired (Tom, 2026-10-31, [Spec 029](docs/knowledge/specs/retired/029-portable-records.md) and [Spec 034](docs/knowledge/specs/retired/034-shadow-run-stream.md)). The retired system’s contract 008 remains the format for its own records store, and its contract 009 retirement was its own follow-up. Backup snapshots remain the durable copy of the store, and any export directory, stream file or journal row a build already wrote stays as inert history that nothing reads or appends.

`snapshot` (`queue.snapshot`) is the live-fleet compatibility read. It returns compact live tasks only — no event histories, handoff text or terminal rows — plus profiles, pool and availability. Optional `repository` (an `owner/name` origin or a checkout path), `project` (project key) and `limit` (default 100, maximum 250) combine with AND; page forward with `cursor` while `hasMore` is true. If any service response exceeds the 16 MiB frame bound, the service returns a typed `oversize` error naming the method, response size and ceiling. Use `queue.detail` for one task's history and `outcome-search` for terminal rows.

`outcome-search` (Spec 025) answers "what landed for X" from the permanent outcome rows. Every filter is optional and filters combine with AND: `repository` (an `owner/name` origin or a checkout path resolving to one), `text` (stemmed full-text search over title, brief text, review summary and reason; space-separated terms), `lane`, `outcome` (`done` by default, `cancelled` or `superseded`), `since`/`until` (inclusive ISO timestamps on `finishedAt`), `commit` (a hex prefix of 7–40 characters matching the merge commit, synced commit or reviewed PR head — run it after `git log -- path`) and `pr` (PR number, requires `repository`). Results are compact rows newest first: reference, title, repository, outcome, lanes, PR number and URL, merge commit, finish time, backfill flag, replacement task id and, for a text search, a short excerpt naming the matched field. Brief text never comes back in bulk; the full row stays one `queue.outcome` call away. `limit` defaults to 20 with a maximum of 100; page forward by passing back `cursor` from the previous response alongside `hasMore`.

Papercuts live permanently in Nucleus. Add one with `papercut.add` using `repository` as `{origin:"owner/name",path:"/checkout"}` or the origin string `papercut.list` takes, plus `title`, `happened`, `impact`, optional `area` and `fix`. `papercut.list` filters by repository origin and state (`open` by default); `papercut.get` takes its id and returns the current version. Edit with `papercut.edit` using `id`, the current `version`, any of `title`, `area`, `happened`, `impact` and `fix`, and optional `author`; a stale version is refused and earlier field values are kept in history. Empty `area` and `fix` clear those fields. Editing a promoted or closed papercut leaves its lifecycle and links unchanged. `papercut.promote` takes the papercut id and either a Nucleus `taskId` or `reference` such as `repo#004`. `papercut.close` takes the id, `reason` (`completed` or `deprecated`) and optional `note`. Closed and promoted records remain queryable.


### Planning records (Spec 026)

Every lane list below follows Spec 019: each lane exists, is `active` or `paused`, and lists the record's repository (for a lead, one of its repositories). One bad key refuses the whole change. `papercut.set-lanes` takes `id` and the full `lanes` list.

Triage leads are permanent. `lead.add` takes `repositories` (one or more `{origin,path}` objects or origin strings; `repository` is the one-item alias), `title`, optional Markdown `body` (up to 1 MB), `lanes`, `tags` and `author`. `lead.edit` takes `id`, the current `version`, `body`, optional `title` and `author`; each change keeps the earlier body as a version and a stale version is refused. `lead.get` returns the lead, the latest version in full and metadata for earlier versions (version, digest, check, approval, author and creation time); while a check is pending, `checkOperationId` identifies the durable operation. Historical bodies are omitted from this summary. It also returns `promotedTaskId` when there is exactly one task target; `targets` lists each target for multi-repository leads. Use `lead.version` with `id` and `version` to read one full historical version. `lead.list` filters by `repository`, `lane` and `state` (`open` by default, `promoted`, `dropped` or `closed`). `lead.set-lanes` replaces the lane list; `lead.set-tags` replaces tags. `papercut` is a reserved, permanent tag set by `papercut.add`. Use `papercut.*` for papercut-specific changes. `lead.drop` needs a `reason`. `lead.reopen` takes `id`, a nonempty `reason` and `author`, and restores one dropped, non-papercut lead to open in place: id, title and body, content version, saved versions, checks, approval history, author, repositories, lanes and targets are unchanged, no version is recorded, and the lead is editable again through `lead.edit`. Any lead that is not dropped is refused, targets are never unpromoted, and reopen triggers no dispatch, check, approval or promotion. The reopen is durable inspectable history: `lead.get` carries `reopens`, one entry per drop–reopen cycle with the reopening reason, actor and time plus the prior drop's reason and time, preserved even though the current dropped-state fields clear. The retired portable-record export omitted the local reopen audit; the stored lead carries it, and the current state reads truthfully. `lead.promote` marks a lead promoted by hand with a `question` or `knowledge` target and a free-text `reference`; each promotion adds a target. `lead.import` takes the same repository identity and `path` to one Markdown file or a `docs/triage/` directory: each file becomes one lead titled by its first heading. It is idempotent on a content key, supports `dryRun:true`, ignores optional `author`, and reports imported, duplicate and unparsed files; `README.md` and files without a heading are reported unparsed. The importer never deletes source files. A schema refusal is one line naming the field and expected shape.

`lead.promote-task` promotes an approved brief-bearing lead; `papercut.promote-task` builds a brief from the papercut and admits it directly. CLI calls require `id`, `agent` and a note naming operator authorization. A lead with several repositories requires `repository` per promotion. Board approval records `operator (board)`. Promotion records a durable operation before the pushed-head check. Quick calls return the task; slower calls return an operation ID and state for `queue.operation-status`. Repeating a promotion for the same lead version or papercut revision returns its existing operation or linked task. On a timeout, the CLI reports an unknown outcome and directs callers to inspect the source record or returned operation ID before retrying. The task and outcome retain the planning source.

Operator decisions record a question an agent needs the operator to rule on, so it is not lost in chat. `decision.add` takes `question`, `askedBy` (the agent id), optional `project` as `{origin,path}` or an origin string, optional `context`, `options`, `recommendation`, and links (`tasks`, `leads`, `papercuts`). `decision.get` returns one with every version; `decision.list` filters by `status`, `asker`, `project`, `task`, `lead` and `papercut`. `decision.answer` takes `id`, the current `version`, the operator's words in `answer`, and `answeredBy`; the board and the Paseo pill answer as `operator (board)` with `relayed:false`, while an agent relays with `relayed:true`, its own id and a `note` quoting the operator. `decision.withdraw` takes `id`, `version`, a `reason` and optional `withdrawnBy`. `decision.link` adds links to an open decision in place — `id`, `version`, and any of `tasks`, `leads`, `papercuts` — so linking never supersedes it or changes its id; omitted lists and already-linked entries are unchanged, and a call that adds nothing writes no version. `decision.supersede` replaces an open decision with a new one in one step and takes the replacement's question fields plus `by`. Every change is versioned and a stale version is refused. Answering sends one durable notice to the asker's thread, deduplicated per version; a decision whose linked tasks, leads and papercuts are all terminal reports `stale:true` and stays open until withdrawn. In Paseo, an agent with an open decision shows a composer pill on its thread — "Decision needed" for one, "N decisions" for more — from its first open decision until every decision it asked is answered, withdrawn or superseded; the pill appears and clears within one board refresh, and its popover shows each decision's question, options and recommendation with an answer box and a link to the board. Decisions record rulings only: they grant no execution authority and change no task, lead or papercut state.

Each lane has one working document. `lane.document.get` takes `key` and an optional `version` (latest by default; `null` before the first save). `lane.document.edit` takes `key`, the latest `version` it was written against (`0` for the first), `text` (up to 128 KB) and `author`; a stale save is refused with a reload prompt and writes nothing. A brief or handoff that sets `queue.laneDocuments: [key]` carries each linked document into worker and reviewer prompts at the version current at first dispatch. The task, each run and the outcome row record the key, version and digest; later edits never change them. Each linked lane must accept the task and hold a document. Without a link, prompts and records are unchanged.

A project plan orders its lanes. `plans` returns every project's current plan in one call. `plan.get` takes `project` (a Spec 027 key) or `repository` and an optional `version`. It returns the saved order for open lanes that still list a member repository, then any other open listing lane in creation order. `plan.set` takes the target, the latest `version` (`0` for the first), `entries: [{lane, note?, horizon?}]` and `author`; `horizon` is `now`, `next` or `later` and defaults to `now`. An optional `idle` reason marks a plan with no now or next lane as intentionally idle, which answers the drained-board prompt until new work finishes or the plan changes (Spec 041). Stale saves and lanes that list none of the project's repositories are refused.

### External PR review entry

An operator can bind an existing isolated Paseo workspace and same-origin open PR directly to independent review. Preview runs the full workspace, Git, planning, PR, permission, author-attestation and ownership proof without storing a task:

```sh
node bin/nucleus-review-entry.mjs --preview review-entry.json
node bin/nucleus-review-entry.mjs --key stable-review-entry-key review-entry.json
```

The input pins the normal `submission`, `workspaceId`, `prNumber`, exact branch/head/current base, takeover authority, and a concrete declared author-model set with GitHub author and provenance. Start uses the durable `review_entry` operation and returns immediately with a receipt. Acceptance is not binding or dispatch. The first task agent is an independent reviewer; no initial worker or worker completion is fabricated. Approval uses the ordinary exact-head verification, merge and closeout gates. Changes requested create the first worker in the same workspace and PR after the reviewer releases it. Pre-existing external workspaces are preserved by default. Set `workspaceOwnership: "intake"` only for an isolated workspace created specifically for this intake; after successful closeout it uses normal guarded workspace archival. Branch commits remain preserved. Cancellation still preserves imported work.

## Worker completion

Workers receive task/run identity, a secret token, and a callback helper through their environment. They send `blocked`, `error`, or `ready_for_review` with a summary. Ready for review requires a PR number. A successful receipt acknowledges durable storage, not PR validation or review approval.

Callbacks are idempotent for identical event IDs and content. Conflicting receipts and stale runs are rejected. After delivery, the worker must stop editing and finish its turn. On reconciliation, an open non-draft GitHub PR must match the expected branch, base, and clean worktree HEAD before the task reaches `awaiting_review`. Verification failure retains the reservation and reports `needs_attention`; correcting an accepted result is not yet exposed as a control.

`refs/stash` is shared by every worktree of a repository, so every worktree-facing prompt forbids `git stash`, and Nucleus itself never runs it. Nucleus records the stash list when it creates a worker or revision run. When a readiness, checkpoint or absent-run check finds the worktree dirty, the refusal names any stash entry popped or dropped during the run that was not taken on the task's branch, and any entry that appeared naming another Nucleus branch.

## Resolution

The plugin creates each worker on an immutable queue-owned branch, supplies that branch in the prompt and environment, and verifies it before launch and ready-for-review. A callback receipt stores worker evidence durably; the task accepts readiness only after the worker releases and the plugin verifies an open PR from that exact branch to the recorded base, with its remote head equal to the clean local worktree head. After a valid PR report and a released worker, the plugin creates an independent reviewer in the same workspace. The reviewer posts a GitHub comment bound to the run, head, and verdict. Changes resume the original worker, including a retained session-persistent worker that has closed after release; subsequent review resumes the same reviewer. The workspace lease prevents overlapping managed turns.

Approval starts Nucleus-owned mechanical gates over durable evidence; no agent is created and nothing reruns full QA, broad Effigy selectors, content validators or worker/reviewer suites. The plugin checks the current PR head and base, visible checks, review decisions, unresolved review threads, mergeability, and a clean synchronized integration checkout. Pending checks wait. A repository with `checksPolicy: "required"` makes only GitHub's own required checks gate; its other hosted results are recorded as advisory evidence and never return the worker, hold the integration turn or request a rerun. That policy can only be set on a repository whose required-check surface Nucleus can positively read; an unsupported plan, unreadable or non-canonical answer is refused before the setting is written. A required check pending well past its recent durations for that name in that repository (or 30 minutes with no history) raises attention naming the job and its URL; the integration turn stays held so a coordinator or operator can rerun it. A terminally failed required check is a semantic refusal: the same PR returns to the retained worker through the ordinary revision loop, counting against the semantic revision budget, with every failed check's name and job URL in the task reason; attention stays for check-infrastructure failures — a required check pending past its deadline — and for an exhausted budget. An accepted exact-head review stays valid when `main` moves with a non-overlapping commit. GitHub `BEHIND` is mergeable when checks, threads and review requirements still pass; a conflict or a branch rule that requires the head to include the current base returns to the worker for a fresh exact-head review. Reviewed tasks take a durable per-repository FIFO integration turn through verification, merge, sync and closeout, so a later PR cannot overtake. A changed base repeats only the mechanical gates. Required GitHub rules remain enforced; merge queues are not implemented.

The plugin records merge intent before a GitHub REST merge request bound to the reviewed head. An uncertain response is reconciled by reading GitHub, never blindly issuing another merge. A verified merge proceeds to a clean fast-forward-only local main sync. Dirty or divergent main is preserved. Merge and sync are separate durable stages, so sync failure cannot repeat the merge.

The retained coordinator verifies acceptance, completes routine canonical closeout Markdown under `docs/logs/`, `docs/roadmaps/` and `docs/handoffs/`, then reports `closed` or `blocked`. This is the fallback route for manifest repositories that bind no authoritative integration-write `task.closeout` hook and do not select Nucleus closeout; such a hook, a v5 `closeout: "queue"` selection, or a repository with no manifest (unless the project setting overrides it to `agent`) owns closeout instead and needs no closeout thread or workspace. It publishes the scoped documentation batch on the clean integration branch under repository policy and reports `closeoutCommit` with the final pushed SHA. Missing routine closeout records are part of this assignment; new planning decisions, broader repairs and missing acceptance evidence still block. The plugin verifies the original merge, published tip, ancestry, clean checkout and allowed Markdown paths before recording completion. The exact submitted handoff may be deleted when repository policy requires disposition; every other changed path must remain a regular Markdown file. Other plugin merges wait during closeout. Attention notices remain mandatory and origin-routed. Completion is quiet unless the frozen cohort is non-empty; routine completion notices wait until each recipient is idle. Explicit coordinator escalations can reach a running planning thread. Uncertain delivery requires inspection, not automatic resend.

Role callbacks use distinct credentials and allowed statuses. Review binds to the exact head; coordinator results also bind to the current assignment generation. A stored callback never authorizes an action while paused. Threads must finish before a result advances the task.

A task waiting on the operator shows the pending native question and its answer controls in the detail, beside the summary, and an answer there is the same native request the thread's question pill resolves. The detail panel leads with a summary a person can read in ten seconds: one plain sentence for the current stop or wait and who acts, each hold with its holder, reason and age, the review round against its allowance with the latest verdict, the `used / limit` budget bars, the latest check results as short ticks, and the newest report's headline with its author, role and age behind **Read full**. Only the two or three owner verbs that fit this state lead; the rest sit behind **More**, and a verb that does not apply is not offered. Below that, three collapsed groups hold everything the dialog always showed: **Activity** (the event timeline), **Runs & agents** (runs, agents, models, profiles, coordination, delivery and completion cohort) and **Technical** (routing, demand, telemetry, validation, QA, hooks, operation receipts, raw identity and the remaining queue controls). A responsible task does not render the old-lifecycle owner, coordinator and incident panels or the top-level demand table. The detail panel also shows run history, delivery outcomes, a missing-result callout when a worker, revision or reviewer run stopped without an accepted report, merged commit, coordinator remapping, **Retry resolution check**, and **Replace absent resolution run**; owner verbs (`restart`, `move` and the rest) apply from the detail's action row, beside the summary. A late authenticated report on that same run identity recovers the hold; unknown delivery is never retried blindly. Retry refuses unresolved thread/delivery leases. It can resume a blocked resolution role or recheck a repaired condition; closeout retries synchronize main again. An uncertain reviewer or closeout creation with no agent ID uses `restart` after a fresh empty exact task/run lookup; generic retry still refuses that unreleased intent. For an existing open unmerged PR, `move to=work` with an `instruction` sends one operator-approved instruction: the plugin persists it with the task, binds it to exactly one revision run, shows it in task detail, and delivers it to the retained worker once as a distinct source beside the immutable handoff and public review findings. Without an `instruction` the move keeps the pending instruction or the review findings. A blocked initial worker with no PR can instead use `restart role=worker` with an explicit bounded instruction. That creates a fresh authenticated run on the same idle worker and workspace; it never repeats the old prompt or one-shot authority implicitly. It does not erase an uncertain merge intent. A permanently failed merge request needs explicit recovery after inspecting GitHub. An escalated recovery or incident whose question has been answered is closed rather than only silenced: the operator-only **Resolve escalation** control takes the required operator reason rather than a PR number or head, moves the escalated episode to `resolved` with the `recovery_escalated` event kept intact as evidence, settles pending attention notices and clears attention, and applies only once no run is unreleased and the escalation is not backed by live work. A refusal names an unreleased run's role, or the active recovery, merge, task lane and phase, or unresolved attention fault that still blocks resolution. It is never available to a coordinator and never happens automatically on cancellation or supersession.

A task refused before any dispatch side effect can use `restart` from `needs_attention` after the cause is fixed. It returns to `queued` through the ordinary episode closure — the incident resolves, recovery and attention clear, pending attention notices settle — and runs current dispatch validation again, retaining the refusal and escalation events as history. A re-pin is refused before dispatch: resubmit the changed handoff and supersede the old task. Re-pin behavior after dispatch is unchanged.

## Persistence and recovery

The data home is `~/.nucleus`, or `NUCLEUS_DATA_HOME` when set. One resolver
(`shared/data-home.mjs`) names it, reads no journal, and ignores `PASEO_HOME`.
A non-empty `~/.nucleus` without Nucleus store markers is refused. `nucleus
data-home` prints the resolution and the path inventory; the full rules are in
the [release contract](docs/knowledge/contracts/release.md).
`queue.sqlite` and the files below are unchanged:

- `queue.sqlite`: WAL SQLite database, submissions, route assignments, task events, role runs, notification intents, receipts, durable hook outbox, permanent outcome rows, durable lanes, task numbers, permanent project settings, and token hashes. Migrations preserve pause, limits, settings and identities. Schema 15 adds outcomes, schema 16 adds lanes, schema 17 adds the permanent per-repository number ledger and backfills retained tasks in creation order, schema 18 adds the papercuts table, and schema 19 adds the former per-repository settings table; it starts empty and nothing else changes. Schema 21 adds the outcome search projection (Spec 025): indexed filter columns and an FTS5 index built from the existing rows; outcome rows and their content stay unchanged, and the projection is rebuildable from them. Schema 22 converts lane membership from one key to a list on every task and outcome row (`lanes`, with one outcome lane index row per task and lane), keeps every row and its dates, and drops the single-key column. Schema 23 preserves those settings rows in `repository_settings` and adds project membership records. Schema 24 adds triage leads with body versions, lane documents and project plans; existing papercuts read with no lanes and existing tasks, runs and outcomes with no lane document pins. Schema 25 gives every project a primary repository: existing defaults use their sole member and existing named projects use their first listed member. Schema 27 sets existing projects to active visibility and version 1. Schema 28 converts unpromoted drafts into checked, approval-bearing leads while retaining their history rows. Schema 29 migrates papercuts into tagged leads and makes the legacy table read-only; schema 30 adds the operator decisions table; schema 31 adds the contract 009 shadow-stream journal, retained as inert history now that the producer is retired. Schema 32 adds milestone QA runs (task 104): durable per-run history in `project_qa_runs`, starting empty with existing records untouched. Schema 33 adds the bounded latest-per-repository index for the QA board read, backfilled from history. Schema 36 (Spec 040) marks every held task past `queued` as a merge hold and gives holds with no reason the origin agent as owner and the reason "not recorded". Schema 48 (Spec 056) adds `repository_rekeys`, the durable receipt of each applied repository namespace re-key; it starts empty and no existing record, counter or identity changes. Older binaries refuse a newer store; rollback requires a compatible reader, never deletion or live database rewriting.
- `settings.json`: daemon URL, optional password, an optional `uncertainMergeRetryMs` (defaults to 120000; bounded to 30 minutes) and the optional `effigyRuntime` setting (`{"minVersion": "0.14.0"}`; the retired `{"path", "sha256"}` pin is accepted and ignored). Default daemon URL is `ws://127.0.0.1:6767/ws`. Nucleus observes an admitted heavy run with the Effigy that actually launched it, found from the admission hook's attested process chain and never from PATH, so an Effigy rebuild needs no settings change; `minVersion`, when set, refuses an older Effigy, and a run whose chain holds no Effigy is refused before it reserves ([Spec 035](docs/knowledge/specs/035-host-run-scheduler.md), "Runtime identity"). Nucleus never resolves the observer through `PATH`, and an old reservation row without a verified binding is never observed.
- `shadow-stream/`, `shadow-seeds/`: retained contract 009 history from the retired producer (`stream-NNNN.jsonl` segments and their seed exports). Nothing appends to or seeds these directories any more; the operator may read or archive them.
- Retired `runners.json` and `runner-artifacts/` remain in place and unread; a data move may copy them as unknown durable entries.
- `callback.sock`, `worker-report.mjs`: local callback endpoint and generated helper.
- `tickets/`: mode-600 assignment files containing callback credentials for retained threads. Credentials are absent from UI/history; the database stores their hashes. This is trusted local code, not a sandbox between agents.
- `isolation/`: Nucleus-owned hook workspaces and prospective-merge candidates, keyed by a digest of the repository git common dir. They live here so resolvers that walk parent directories never reach a repository checkout. Checkouts recorded under a repository's former `.git/queue-hooks` root remain owned until ordinary cleanup removes them. Per-run milestone QA checkouts live beside it under `project-qa/` in the same data directory and are removed when the run settles.

The backend connects without requiring an open panel and reconciles every 30 seconds plus agent events. It declares app version 0.8.0: omitting that version on this daemon selects an older agent read view and fails to find newly created workers. A process-ownership record prevents concurrent plugin backends from dispatching against the same database.

Creation intent is committed before remote calls. Recovery reattaches only to positively identified task resources. An empty lookup never triggers a blind creation retry. After the uncertain intent has stopped, coordinator recovery or an explicit versioned `restart role=worker` can authorize one replacement only if a fresh exact task/run lookup is still empty and the retained worktree is clean at its recorded base on the queue branch. The plugin then revokes the old callback, retains the workspace/profile and creates a worker under a fresh run identity. An uncertain reviewer or closeout creation with no returned agent ID uses `restart`: it repeats the exact task/run lookup, requires zero matches, revalidates the retained workspace and PR, revokes the absent run's callback, and lets the normal launcher create one fresh run for that role. A failed recovery-coordinator creation with a recorded error and current generation is reconciled in the recovery pass: one exact label match binds, an empty lookup revokes and releases the failed run while keeping the escalation open, and multiple matches stay escalated. An agentless intent without recorded creation failure remains fenced for `restart`; an empty lookup releases it and keeps the escalation open, launching nothing, so `restart` and `move` work again. A parked `restart` never clears an unresolved creation intent. Do not delete the database or manually clear reservations to recover uncertain work; inspect task/workspace/agent identities first. On worker quota exhaustion, replacement waits for the old thread and all earlier workers to stop. It selects an eligible worker profile under the original scope and preference rules, records a new run intent, and creates a new agent in the same workspace. Uncommitted files and unpublished commits are preserved; an existing task PR must be reused. A required preferred profile never silently falls back. No eligible profile holds the reservation and reports attention. Up to eight replacements are allowed per task before operator intervention is required.

Old run callbacks cannot advance the new assignment. Known earlier author models remain excluded from review; unknown automatic author identities block proof of independent review. Unknown replacement creation outcomes are reconciled by run identity, never blindly retried. Retired workers remain visible in task detail and count toward pause/quiet observation while the task is active.

Automatic replacement covers initial workers, revision turns, reviewers and coordinators with a known profile/subscription assignment. Reviewer replacement starts a fresh independent review. Coordinator replacement increments its assignment generation and rejects old callbacks; closeout replacement resynchronizes main without re-merging. Existing role-run identities and workspace leases are retained. Unknown creation/delivery outcomes are not treated as proof that another thread should be started. An explicitly assigned external coordinator with no known profile requires manual remapping on exhaustion. Up to eight role replacements are allowed per task.

A stopped initial worker that fails before any callback can be resumed only after coordinator recovery confirms the workspace lease is released and returns an explicit `restart role=worker` instruction. Transport failures follow this path even though no blocked callback exists. The plugin sends a fresh authenticated continuation run to the same retained worker and workspace, preserving uncommitted files and commits. A resumed pre-PR worker can establish the task's first accepted PR from its authenticated revision callback after the normal canonical branch, clean worktree and exact remote-head checks. The older blocked completion is replaced only after that verification succeeds. It never creates a second worker or replays one-shot authority. Replacement remains a separate retry path for a worker proven terminal. If that pre-PR revision then stops without a callback, `restart` requires the same escalated missing-callback incident, confirms the retained worker is idle in its workspace, verifies the continuation worktree without cleaning it, supersedes only the proven stopped run, revokes its callback and arms one fresh authenticated continuation. A missing PR cannot make the task irrecoverable; the post-PR form of the same action keeps its exact branch, base and head checks. When the retained worker repeatedly cannot complete that continuation, owner `restart` applies the same proof, preserves the workspace and PR, retires the old worker, selects a different eligible profile and binds the explicit continuation to one replacement worker run. If profile eligibility checking cleared `currentRunId`, replacement can still target the exact unreleased revision run named by the escalated missing-callback incident; same-worker missing-callback recovery still requires the current run binding.

Provider reset timing accepts exact ISO timestamps with timezone (`providerRetryAt` on an authenticated callback, or explicit reset/retry timestamps in provider errors) and structured `retry_after_seconds` / `retryAfterSeconds` intervals up to 31 days. The deadline is persisted once; repeated observations do not extend it. When it passes the subscription becomes eligible to try again. Missing, past or ambiguous timing stays unavailable until manually reset. The pool shows a known retry deadline; **Reset** can restore eligibility earlier.

## Repository hooks

A repository may opt into lifecycle policy with a committed `.paseo/queue.json`.
Frozen `paseo.queue.control.v1` hooks keep top-level `executable` and `argv`.
`paseo.queue.control.v2` replaces those fields with a `program`: a committed
repository executable or a named tool on the Nucleus service PATH. Nucleus reads the manifest and every repository-local
executable from the clean synchronized base commit, pins path, commit and SHA-256
digest, and runs the pinned regular executable directly with literal `argv` and
`shell: false`. Event content is data: it is never interpolated into the
executable, arguments or environment. The only environment is `PATH`, `HOME`,
`TMPDIR`, `LANG`, `LC_ALL` when present plus non-secret `PASEO_QUEUE_EVENT_ID`
and `PASEO_QUEUE_EVENT_SCHEMA`. Callback credentials and daemon authentication
are absent.

Tool names contain no slashes or interpolation. Nucleus records the resolved real
path and digest on the occurrence, then runs it with literal arguments. A missing
tool blocks required delivery or fails advisory delivery. Legacy runner-shaped
manifests map to tool names; the approval registry is retired.

The closed v1 event set is `task.pre_dispatch`, `task.blocked`,
`task.cancelled` and `task.closeout`. `task.pre_dispatch` is read-only. A hook
declares `read_only` or `integration_write`, and `required` or `advisory`
delivery. The hook receives one `paseo.queue.event.v1` object on stdin and EOF
and must write exactly one `paseo.queue.hook-result.v1` object on stdout.

- Read-only hooks must leave HEAD, index and worktree byte-identical and report
  no changed paths or commit subject. Nucleus refuses and enters attention
  otherwise.
- Integration-write hooks run under the existing repository integration turn from
  a Nucleus-owned isolated checkout created at the exact synchronized event base.
  They may change only declared `allowedPaths`, and must return exactly the
  paths Nucleus's post-run inspection sees. Nucleus stages those exact paths,
  creates the commit with its own event and manifest trailers, pushes normally,
  verifies the remote, fast-forwards the operator checkout to the published
  commit, and removes only the isolated checkout it created. Pre-existing
  ignored operator evidence is allowed and left byte-for-byte untouched; a
  publication that would overwrite ignored content is refused and left for
  reconciliation. Hooks never stage, commit, push or choose publication scope.
  The event's `repository.root` names the actual execution checkout; the
  isolated path is recorded before creation, so a restart never creates a
  second checkout or removes an operator or agent workspace. A no-diff `ok`
  result records success without a commit.
- A required blocked/failed result holds the transition; an advisory failure
  advances only after Nucleus proves the repository is clean. Manifest absence
  means no repository hooks run at all; closeout for such repositories follows
  the Projects section below.

Closeout authority is selected per repository from the manifest pinned at the
synchronized integration commit. When at least one `required`
`integration_write` hook is bound to `task.closeout`, that hook owns closeout:
Nucleus emits the event from its durable task, review, verification, merge and
synchronized-main facts and marks the task `done` only after the hook publishes
and the canonical checkout is synchronized. It creates no closeout run,
coordinator closeout assignment or closeout workspace. A selected required hook
that blocks, fails, times out, returns invalid output, leaves an uncertain
effect or loses publication identity holds visibly and is never replaced by the
closeout agent; `retry_effect` resumes the same occurrence identity. A v5
manifest with `closeout: "queue"` also owns closeout in Nucleus. A repository
with no manifest at the synchronized commit now behaves the same way: Nucleus
closeout is the default, unless the project setting below overrides it to
`agent`. A manifest repository always keeps its manifest authority regardless
of any project setting, and a closeout already running under agent authority
settles under it. When a manifest binds no closeout hook and does not select
Nucleus closeout, the existing closeout agent runs and any read-only or advisory
closeout hooks run after its verified publication as observers. Exactly one
closeout authority applies per task.

Intent is persisted before every external effect. A retry reproduces the
immutable occurrence — event ID, original occurrence time, repository base,
task identity, delivery object, and manifest and executable pins — and advances
only the confirmed attempt. Pre-migration records recover that delivery from
Nucleus's own durable task, run, review, verification, merge, and closeout state,
or stay blocked when a fact is missing or ambiguous. Restart reconciliation
adopts only one exact local or remote match, fast-forwards the operator checkout
to the synchronized remote, and keeps divergent, ambiguous, dirty or multiple
matches in attention. `taskControl` action `retry_effect` with the recorded hook
record ID or its stable event ID resumes only a reconciled event; it cannot
clear an unknown process, creation, commit, push, synchronization or cleanup
outcome. Hook history and resolved tool evidence appear in task detail.

A repository-neutral submission path (`queue.submit-instruction`) accepts a
committed instruction artifact by path, commit, SHA-256 digest and opaque media
type. The existing Northstar handoff submission is one adapter that fills the
same artifact; Nucleus never parses the document.

## Submit an approved Northstar handoff

Planning threads can now submit one handoff path instead of assembling a task JSON payload:

```sh
node bin/nucleus-submit.mjs /absolute/repo/docs/handoffs/worker.md --dry-run
node bin/nucleus-submit.mjs /absolute/repo/docs/handoffs/worker.md
```

Origin defaults to `PASEO_AGENT_ID`; `--origin AGENT_ID` supplies it explicitly. Optional `--coordinator`, `--base` (default main) and `--commit EXPECTED_HEAD` control assignment and the integration HEAD fence. The `queue.handoff` RPC exposes the same operation. Dry runs do not write tasks or change orchestration settings.

Use a ready-to-launch Northstar implementation handoff, with the standard seven sections, committed and pushed on the integration branch. Add an explicit dispatch declaration and a reference to the operator's execution authorization before committing:

```yaml
queue_dispatch: nucleus
queue_approval: "Operator approved execution in the originating thread"
queue:
  scope: general
  complexity: medium
  skipPRReview: false
  notifyOriginOnCloseout: false
  completionNotificationAgentIds: []
```

Optional queue fields: `preferredProfileId`, `requirePreferred`, `thinkingOptionId`, `dependsOn`, `lane` or `lanes`, `notifyOriginOnCloseout`, and `completionNotificationAgentIds`. `queue.lane` takes one lane key or a list and `queue.lanes` takes a list (giving both is refused); each lane must list this repository and be active or paused, or dry run and submission refuse the whole set. Every new task runs the responsible lifecycle ([Spec 058](docs/knowledge/specs/058-responsible-tasks.md)); explicit `queue.responsible: false` is refused, and `queue.manualVerification: true` cannot select the old lifecycle. Omit routing fields to let the pool choose. Omit completion policy for quiet closeout. Handoff dry runs validate nominated recipients without storing work. Review skipping requires task-specific operator authorization. Promotion alone does not authorize execution. The adapter checks structure and Git state; it does not replace Northstar semantic readiness checks or infer dependencies from planning documents.

Task identity follows the last committed revision of the handoff, so retries survive unrelated main commits without duplicate work. A revised handoff creates a new identity: inspect or cancel an earlier task before submitting its replacement. Unrelated dirty files can remain during submission, but dispatch still requires a clean integration checkout. Submitting while paused stores work without starting it.

### Submit a brief held by Nucleus

For a repository whose `.paseo/queue.json` is v5, or that has none, a brief can travel as content instead of a committed handoff (Spec 020):

```sh
node bin/nucleus-submit.mjs --brief --repo /absolute/repo /absolute/path/brief.md --dry-run
node bin/nucleus-submit.mjs --brief --repo /absolute/repo /absolute/path/brief.md
```

The file uses the same frontmatter and seven sections as a handoff but need not be committed or live under `docs/handoffs/`. The planning commit is the pushed integration head: Nucleus fetches `origin/<base>` and records that head, so a shared checkout that is merely behind origin still plans from what is pushed, and manifest eligibility is read there rather than at the checkout's HEAD. The integration checkout must be clean and on the base branch. The dry run returns the brief's digest. v1–v4 repositories are refused. Nucleus pins the text by digest, delivers it inline to worker, revision and reviewer prompts, and never writes it to the repository. Submission identity follows the repository and brief digest, so resubmitting the same brief finds the same task. Before merge, operator `amend_brief` on `queue.task` (with `brief` text and `reason`) pins a new version; the next run gets it with the reason. After merge it is refused. A re-pin (`amend_brief` with no text) applies only to committed handoffs. The outcome row keeps the final brief, its digest and the digests it replaced.

The agent-facing skill is `skills/nucleus/SKILL.md`, the only skill the package
installs. It owns planning records, briefs, leads, papercuts, decisions, project
QA and planner handover. Documentation structure stays in the Northstar skill.
The low-level `queue.submit` RPC and `bin/queue-cli.mjs submit` remain available
for other producers.

### Brief-bearing leads

`lead.submit` accepts `{repository, title, body, agent, note}` and optional
`baseBranch`, `lanes`, `tags`, `hostId` and `hold`. It adds the brief-bearing lead,
waits for its check, records the caller's authorization note as relayed approval,
and waits for promotion to return `{taskId, reference}`. Failed checks return
`{lead}` with findings. An existing same-title lead or task in the repository is
returned without duplication; existing leads are left unchanged. All individual
lead methods remain available.

A lead body can hold the full brief Markdown, including frontmatter. `lead.add` and `lead.edit` record each version before queuing its pushed-head check as a durable operation. Quick checks still return the checked lead; while a check is pending, the returned lead and `lead.get` include its `checkOperationId`, and `queue.operation-status` reports progress or failure. The settled check result is stored on that lead version. `lead.check` refreshes the latest check. `lead.approve` binds to its exact version and digest; a CLI agent supplies an authorization note and records relayed approval, while the board records its own operator action. Editing clears approval. `lead.promote-task` rechecks through a durable operation before one transaction admits the task and links the lead. A refusal leaves the approval and records the fresh check; an unfinished operation is observable with `queue.operation-status`. Existing unpromoted draft rows migrate to approved or unapproved leads with every version; old rows stay readable as history.

## Remove a task

Select a stopped task and use **Remove from queue**. Queued, blocked, error, needs-attention, cancelled and completed tasks can be removed once their threads have stopped and no creation, retained run or merge is unresolved. Running tasks must finish or stop first. Removal is serialized with orchestration work and checks thread state again.

Removal first archives every idle worker, reviewer, recovery, and coordinator thread attached to the task, then archives the task-owned workspace. If any thread is active, the workspace is dirty, unpublished, shared or identity-ambiguous, or either archive operation fails, the task remains visible and removal fails. Workspace archival removes its worktree and ignored evidence; the retained task history must carry the evidence needed after removal. Remote branches and PRs are not deleted. After resource resolution, removal hides the task, revokes its callbacks and suppresses pending origin notices. A repeated submission returns the retained removed task instead of launching duplicate work. History remains available through `queue.detail` using its task ID until retention purges it.

API: `queue.remove` accepts `{ "taskId": "...", "version": 1 }`; the version must match the current task. Available through `bin/queue-cli.mjs remove payload.json` as well as the task detail button. Removal is a durable operation: a fast removal still returns the task, while a slow one returns `{"accepted":true,"operation":{...}}` for `queue.operation-status` observation, and repeating the same task and version replays the same operation. An already-removed task returns as removed.


## Task dependencies

Submit prerequisites first, then put their returned **task IDs** in `dependsOn` on a task submission. The Northstar handoff adapter accepts the same list in its committed frontmatter:

```yaml
queue:
  dependsOn:
    - prerequisite-task-id
    - another-prerequisite-task-id
```

All prerequisites must reach `done` before dispatch: merge, main synchronization and coordinator closeout have completed. Worker completion or a review-ready PR is insufficient. Dependencies may span projects. Waiting tasks stay queued, consume no dispatch slots, and do not hold up independent work. Pause and capacity limits still apply after prerequisites finish.

Task cards show the prerequisite count and waiting reason; task details link to prerequisite states. Blocked, failed, cancelled or removed unfinished prerequisites keep dependants waiting. Removing a completed prerequisite preserves its completion and history. Resolving a blocker and completing the prerequisite releases dependants on the next engine pass.

References must exist and dependency graphs must remain acyclic. Before dispatch starts, an authorized agent can replace a queued task's complete prerequisite list without replacing the task:

```sh
node bin/nucleus-dependencies.mjs TASK_ID PREREQUISITE_TASK_ID ANOTHER_TASK_ID
```

Pass only `TASK_ID` to clear the list. The versioned action preserves task identity and rejects missing, duplicate, removed-unfinished, self and transitive-cycle references. Once workspace or worker dispatch begins, dependencies are frozen. An unchanged submission retry still uses the committed handoff's original identity even after an explicit graph edit. Handoff dry runs validate references against the queue without storing work. The plugin does not infer these links from Northstar documents.

## Project queue promotion

An authorized operator or agent can move a task to the front of its project's queued work without holding, cancelling or replacing anything:

```sh
node bin/nucleus-promote.mjs TASK_ID
```

Promotion applies only while the task is awaiting dispatch. It preserves task identity, dependencies and the relative scheduling slots occupied by other projects; only the order of queued tasks from the same repository changes. Capacity, pause, hold and dependency gates still apply. Repeated promotion of the current project leader is idempotent.

The task detail modal exposes **Promote in project**. Direct RPC clients can send `queue.task` with the current `taskId`, `version` and `action: "promote"`. Planning-thread sessions use the CLI helper. Nucleus-run agents use `nucleus_report`, `nucleus_ask` and `nucleus_message`; owner controls stay in the CLI.

## Lanes

A lane is an opt-in grouping for related work, including work that spans repositories. It does not gate dispatch. Create or edit through the CLI; the board Lanes table is read-only.

```sh
node bin/queue-cli.mjs lane.upsert payload.json
node bin/queue-cli.mjs lane.status payload.json
node bin/queue-cli.mjs lanes payload.json
```

`lane.upsert` takes `key`, `title`, `aim` (up to 2,000 characters) and `repositories` (`origin` as `owner/name`, plus a local path hint). `lane.status` sets `active`, `paused`, `done` or `abandoned` with an optional note and never touches attached tasks. `lanes` lists by optional status and repository, with live counts and recent outcomes.

Attach at submission with `queue.lane: <key>`, `queue.lane: [<key>, <key>]` or `queue.lanes: [<key>, <key>]` on a handoff or brief; giving both `lane` and `lanes` is refused. Every lane must already exist, list the repository, and be active or paused; one unknown, closed or non-listing key refuses the whole submission and nothing is attached. A task belongs to zero or more lanes, keeps the order given, and keeps one identity, workspace, execution and outcome. On a live task, `queue.task` `set_lane` takes the full `lanes` list (an empty list clears; the single `lane` input means a one-item list or none) and changes nothing else. The outcome row records `lanes`, so history survives task purge and `outcome-search` finds a row under any of its keys. Worker and reviewer prompts carry one title-and-aim block per lane in list order as context, not authority.

## Projects

Nucleus stores projects as permanent host-neutral records with a unique key, a name, one primary repository and any secondary repositories (normalised origin and local path hint). Every repository starts in its own project. `project.upsert` can group repositories; a repository cannot join two named projects. The primary leads the returned repository list and is the default for project-scoped views and the project plan. Removing the primary requires naming a replacement in the same upsert; removing another member returns it to a single-repository project. Tasks, numbers, outcomes, lanes and repository settings retain their repository keys. The board filter scopes tasks, leads, papercuts and lanes to all members of the selected project. A task number displays as `repo#N` in a multi-repository project and `#N` in a single-repository project. A task in a multi-repository project gets a read-only sibling worktree of each other member repository, detached at the fetched `origin/<base>` under the Nucleus data directory (`siblings/<taskId>/<repository name>`); the worker, revision and reviewer prompts name those paths as read-only by rule. Each run records every sibling's commit and the outcome row keeps them; a moved head, new commit or dirty files becomes a sibling-change finding in task detail and the reviewer input, never merged or pushed. `queue.siblings: false` on a handoff or brief skips them. Cleanup, cancellation and purge remove sibling worktrees with the task's own and never touch operator checkouts. Separately, Nucleus fast-forwards clean detached sibling clones that already sit beside the task worktree in the Paseo worktree root (the checkouts relative paths such as `../name` resolve). Dirty, branched or diverged checkouts in that root are reported and left untouched; fetch failures never block dispatch.

Closeout, prospective-merge and review settings are repository settings, stored separately in `repository_settings`. A repository with no `.paseo/queue.json` at the synchronized commit gets Nucleus-owned closeout by default. A repository that needs agent closeout sets `closeout: "agent"`; a manifest still governs its repository. A repository that wants branch protection to enforce independent review sets `reviewer: {login}`: Nucleus then publishes each accepted verdict as a formal GitHub review from that login, pinned to the reviewed head, and merges only on that login's approved review at the current head. Its token is read at call time from the macOS login keychain (service `paseo-queue.github-reviewer`, account `<org>`) and is never stored or logged. Repositories without the setting keep the existing review-comment path. A reused local path cannot carry another origin's setting.

Manage both records through the CLI:

```sh
node bin/queue-cli.mjs project.upsert project.json
node bin/queue-cli.mjs project.get project-query.json
node bin/queue-cli.mjs project.park project-version.json
node bin/queue-cli.mjs project.unpark project-version.json
node bin/queue-cli.mjs project.remove project-remove.json
node bin/queue-cli.mjs project.removal-blockers project-query.json
node bin/queue-cli.mjs projects
node bin/queue-cli.mjs repository.set settings.json
node bin/queue-cli.mjs repository.get repository-query.json
node bin/queue-cli.mjs repositories
node bin/queue-cli.mjs project.qa.run qa-request.json
node bin/queue-cli.mjs project.qa.cancel qa-cancel.json
node bin/queue-cli.mjs project.qa.get qa-query.json
node bin/queue-cli.mjs project.qa.list
```

`project.upsert` takes `{ "key": "suite", "name": "Suite", "repositories": [{ "origin": "owner/repo", "path": "/checkout" }, { "origin": "owner/other", "path": "" }], "primary": { "origin": "owner/repo", "path": "/checkout" } }`. The primary must be listed; it is required for several repositories and defaults to the sole member otherwise. A path may be empty when only the origin is known. `project.get` takes `{ "key": "suite" }` or `{ "repository": { "origin": "owner/repo", "path": "" } }`. Old string-shaped `project.get` calls refuse with a pointer to `repository.get`. `project.set` is removed; repository settings are written with `repository.set`.

Projects have `visibility: "active"` by default and a version. `project.park` and `project.unpark` take `{ "key": "suite", "version": 1 }`, using the current version returned by `project.get` or `projects`. Repeating the current state with the current version leaves it unchanged; a stale version is refused. Parking hides ordinary work from All projects without stopping tasks, threads or workspaces. The selector has a Parked section with Unpark, Planning groups parked projects, and attention from parked projects remains visible with a parked marker. Selecting a parked project still opens its views and workspace board.

`project.remove` deletes a stale or duplicate project record for good and is operator-only: `{ "key": "suite", "version": 1, "reason": "why it is going away" }`. It is version-checked and refuses, naming what blocks it, while the project has a task that is not done or cancelled, an open lead, papercut or decision, an active lane, or a pending submission. History stays: outcomes, closed leads and events keep their repository identity and still resolve for search and export, and the repository settings row is removed only when no other project uses it. Deletion writes a tombstone so an export or import never resurrects the project, and it never touches Paseo workspaces, checkouts or git state. The Planning tab offers Delete on a parked project only, and its confirmation names any blockers. `project.removal-blockers` takes `{ "key": "suite" }` and returns that same blocker list — the board's confirmation reads it from Nucleus rather than recomputing it.

Renaming a repository on the forge does not move Nucleus's records by itself. `repository.rekey-preview` takes `{ "source": "owner/old", "target": { "origin": "owner/new", "path": "/optional/new/checkout" }, "expectedSourceRevision": 12, "reason": "…", "idempotencyKey": "…" }` and reports, read-only, what a fresh apply would move and what it would refuse. `repository.rekey` takes the same payload plus `author` (and `relayedBy` when an agent relays the operator) and applies it as one durable `repository_rekey` operation: settings, numbering (including purged tasks' permanent numbers), live tasks, outcomes and their search identity, leads, lanes, brief drafts, decision targets, project membership, QA runs and the QA schedule move to the new identity in one transaction; operation payloads, hook events, host-run evidence, the shadow journal, receipts and an outcome's proof stay exactly as written under the old identity. Numbering continues per repository and never restarts at one. Same origin with a different `path` is a path-only step: every path hint of this origin moves, numbering stays, and the source origin is not occupancy of a different repository. Same origin with no path, or the same path, still refuses. When the settings row has an empty path, the step derives the checkout from the source's own records, or takes `sourcePath` when they disagree, rather than silently skipping `repoPath` rows. Nothing touches a checkout, a Git remote or GitHub, and no old-origin redirect survives for another repository to inherit. A target occupied in any current family — even by a bare number counter — refuses, so a swap goes through a deliberately unused temporary name one step at a time; settled host-run history is evidence rather than occupancy, while a running or capacity-holding host run refuses. A record that already names a different origin is never claimed through a shared checkout path, and a path-named source shared by two origin-known repositories refuses as ambiguous. `repository.rekey-receipt` takes `{ "key": "…" }` or `{ "id": "…" }` and returns the durable receipt (old and new identities, path change, reason, author and relay, time, input hash, affected-family counts, numbering facts, moved project and lane keys, and the families left historical); repeating a lost step with the same key returns it instead of applying twice. See Spec 056 for the desktop-final/CLI-takes-name order and the quiescence gates.
`repository.set` takes a repository checkout path or `owner/name` origin and patches the named fields: an absent field is untouched, an explicit `null` clears it, and the result is the full settings row. Fields: optional `closeout` (`queue`, `agent` or `null`), optional `validation` (`{ "argv": ["command", "arg"], "timeoutMs": 30000, "maxOutputBytes": 65536 }` or `null`), optional `reviewer` (`{ "login": "<github-login>" }` or `null`), optional `qa`, optional `checksPolicy` and an optional `note`. `repository.get` answers with the settings row or `null`; `repositories` lists all settings rows. The retired `validationPolicy` field is refused with the replacement named: put that text in the repository's AGENTS.md Validate section, which is the only validation source Nucleus injects a pointer to. `checksPolicy` is `"all"` by default — what an absent or null field means — and every hosted check blocks under it. Set `"required"` to make only the checks GitHub requires for the PR's base branch blocking: Nucleus reads the real required status contexts and app bindings from classic branch protection and applicable rulesets, records every other hosted result at the exact head as advisory evidence on the task, and neither returns the author nor reruns CI for it. Only GitHub's own absent-state answer counts as no classic required checks; an unreadable, refused or malformed answer holds the task visibly instead of merging. Setting `"required"` is itself refused before any field of the patch is written unless GitHub's requirement surface is positively readable for the repository's canonical `owner/name` and its own default branch: GitHub's explicit plan or visibility refusal ("Upgrade to GitHub Pro or make this repository public") names what the owner can do, every other unreadable, unauthorized, malformed or non-canonical answer refuses as unknown, and switching to `"all"` or clearing the field never needs the read. A successful read only permits the setting — it is not cached or treated as merge proof — and a checkout whose recorded origin disagrees with its settings, or a settings write that lands during the read, refuses with nothing written. The policy, and the settings revision it was read under, are rechecked before a merge intent and again before the merge request. Edit these fields in Settings → Projects.

Nucleus runs project validation after accepted review on the exact prospective merge candidate for repositories with no manifest or a v5 manifest. The command runs with literal argv, no implied shell, the candidate as its working directory and Nucleus's minimal hook environment. It must work in a fresh checkout; Nucleus installs nothing. Exit 0 passes. Nonzero exit returns a bounded output tail to the worker as one semantic revision. Timeout, launch failure or candidate mutation holds for operator attention without spending a revision. Base or head movement invalidates the result. The task and terminal outcome record the argv, digest, exit code, duration and output tail. v1–v4 repositories keep their manifest hooks alone.

Project validation runs under Nucleus's contract 010 host scheduler. While it waits, task detail reads "Waiting for QA capacity (position N)"; its queue wait, wall time, CPU and `capacity_timeout` outcome come from the scheduler record and settlement. A capacity deadline is a typed hold retried by the operator, never a validation failure. Worker liveness uses Nucleus's scheduler when it has a client-submitted run for that worktree; a legacy Effigy-only run during rollback is not liveness evidence. Telemetry aggregates queue wait separately from run time per project and task type.

Two operator controls cover a host run's capacity. `host.run.capacity.release` takes `{ "runId": "...", "reason": "why" }` and releases a *settled* run's remaining container or escaped-descendant custody. `host.run.accounting.dispose` is the separate accounting control for a launched reservation whose outcome is genuinely unknown and which may never report a terminal result (for example an admission reservation with no trusted runtime binding): it stops charging that reservation's CPU and memory, and nothing else. It takes the run id, a durable `operationId`, `expectedEpoch`, the `expectedRunDigest` from `host.run.accounting.status`, the operator's `authority` (`{"caller": "operator (board)"}`, or `{"caller": "<agent>", "relayed": true, "note": "<the operator's authorization>"}`) and a separate `acceptance` naming that exact run and epoch with `unknownOutcomeRetained: true`; a changed row, a stale epoch, a known settlement, a second operation and an unreadable disposition all refuse with nothing written. The run keeps its state, settlement, process, containers and history; a retired run no longer holds its workspace ([Spec 035](docs/knowledge/specs/035-host-run-scheduler.md), "Workspace release on retired accounting"). Later authentic evidence records itself without resuming the retired charge ([Spec 035](docs/knowledge/specs/035-host-run-scheduler.md), "Operator accounting disposition"). `host.run.accounting.status` takes `{ "runId": "..." }` and returns the pinned record, the accounting state, the disposition and the record digest; it is also the confirmation read after a lost reply. A launched admission needs no operator for this when its producer reports that exact run's `checkout-journal` cleanup complete: Nucleus retires the accounting automatically then, recording the producer's own record and the operator's 2026-10-25 policy ruling and no operator acceptance, told apart by the disposition's `format` ([Spec 035](docs/knowledge/specs/035-host-run-scheduler.md), "Automatic accounting on producer cleanup"). The automatic path writes no result or settlement, invents no container or descendant inventory and claims no physical headroom, and a failed write or unreadable stored retirement keeps the charge with its reason.

Full QA runs at milestones, not per task. `project.qa.run` takes `{ "repository": "/checkout-or-owner/name", "baseBranch": "main" }` and returns the running record immediately. Add `wait: true` (CLI `project.qa.run --wait`) to return the settled record with `state`, `exitCode`, `failureIndexes` and `failuresLogPath`; the path is null when there are no consolidated failure diagnostics. Waiting preserves the request ID and admitted run; after a lost response, reconcile with `project.qa.request-status`. A second request while one is running returns that run. Nucleus checks the fetched `origin/<baseBranch>` head in a Nucleus-owned linked worktree and never switches or builds in the registered checkout or borrows a task worktree. Setup, QA and teardown each run in a new process group. The supervisor records the process group and start identity, stops groups with SIGTERM then SIGKILL after the configured grace, and settles after the group is proven empty even if an escaped process keeps an output pipe open. A surviving `setsid` descendant is recorded on the run. The `host.run.result` file is owner-only and published atomically; a restarted service settles from it, and reports `lost` only after group death is proven without a result.

The command is the repository's `qa` setting (`repository.set` `qa: {argv, timeoutMs, maxOutputBytes, terminationGraceMs}` or `qa: {stages:[{name, argv, timeoutMs, maxOutputBytes?}], terminationGraceMs}`, timeout up to 2 hours) when set, else `effigy qa`; `terminationGraceMs` defaults to 30 seconds. A `stages` setting replaces the single `argv`/`timeoutMs` with 1 to 8 ordered, slug-named stages inside the run's one admission; each stage is its own recorded step, the first failure stops the run, and each step's full output, capped at its `maxOutputBytes` with the tail kept, is written to a mode-0600 log beside the run whose path `project.qa.get` returns. The per-task `validation` setting is never used here. A non-zero exit is a `failed` result. Timeout, cancel, and lost are separate outcomes; cancel runs teardown. `project.qa.cancel` takes `{ "id": "run-id", "reason": "why" }` and is idempotent. The QA runs tab's run detail offers Cancel for a queued or running run and shows its steps, failed step, duration, output tail and escaped descendants; the Planning tab carries only the latest result as one compact line — state, failed step, commit, time and any capacity wait, plus the escaped-descendant and capacity-unavailable alerts, and its own loading, read-failed and stale notices — linked to that same run detail. `project.qa.get` accepts `{ "id": "run-id" }` or `{ "repository": "…" }`; `project.qa.list` returns the latest run per repository. These runs grant no merge authority and gate no task. Each run is a board card (Tom, 2026-11-01): a passing run leaves the board five minutes after it finishes, and a failure stays until a passing re-run or `project.qa.dismiss { "id": "run-id", "reason": "why", "caller": "who" }`, which records the dismissal on the run and never deletes it. A dismissed run is never shown; a live or passing run is not dismissible.

## Agent reporting through MCP

New plugin-managed agents receive a session-scoped `nucleus` MCP server through Paseo's SDK. No Paseo source changes or global MCP settings are required. The server exposes `nucleus_report` with structured `runId`, `status`, `summary`, a short `headline` (what happened and what is next, at most about 200 characters) and optional `prNumber`, `reviewText`, `providerUnavailable`, `providerRetryAt` fields. Nucleus derives the headline from the first sentence of the summary when a caller omits it, so every accepted report carries one; a report stored before the field existed shows the same sentence. It also exposes `nucleus_ask` for decisions and `nucleus_message` for worker messages, and new launches set `NUCLEUS_*` environment values; the retired `northstar_*` tools and `NORTHSTAR_*` variables are neither advertised nor accepted by a live session. Agents carry only `nucleus.*` identity labels. Credentials and task identity stay in a private session binding. The bridge supplies the expected head and coordinator generation, and the bound run is the report's run: a typed `runId` naming any other run is refused with the bound one named, and nothing is recorded.

When Paseo explicitly rejects session MCP before creating an agent, the plugin
uses the same authenticated local socket callback carried by earlier workers.
Ambiguous creation failures remain fenced. A persisted unsupported-MCP
preflight with an exhaustive zero-agent lookup clears only its failed creation
intent and requires an explicit resolution retry before dispatch resumes.

Reviewers submit the full findings as `reviewText` with `ready_to_merge` or `changes_required`. After the thread stops and orchestration is unpaused, the plugin publishes that text with the exact review marker, verifies the GitHub comment and continues the existing review/merge gates. The publication has a persisted intent and is reconciled after an uncertain response; it is never blindly duplicated. Reports themselves are authenticated and idempotent across restarts.

Retained MCP threads keep their server binding, which advances to each new assignment. Calls must name the current run ID; stale instructions are rejected. Already-created threads retain their working shell callback path. Newly generated legacy reviewer instructions explicitly use `gh api -F body=@FILE`, because lowercase `-f` posts the literal path instead of reading the file.

The installed plugin source must retain `bin/mcp-report.mjs` , its root `mcp-report.mjs` compatibility entry, and its npm dependencies. The bridge needs Node on the agent subprocess PATH and a provider supporting session MCP servers. No tokens belong in prompts or tool arguments. If a resumed provider session cannot expose the tool, generated instructions include a run-specific authenticated helper fallback. It accepts the same result fields, including full reviewer text. A rejected MCP callback must not be bypassed through fallback; only an absent tool warrants using it.

## Workspace closeout and archiving

After a task reaches `done`, the plugin archives its own worker worktree and any recovery worktree it created for closeout. Cleanup runs on the next orchestration pass and respects pause. Task history stays in the queue; details show archive progress or why cleanup is waiting. Blocked, failed and unfinished tasks remain open.

Before archiving, the plugin checks recorded workspace/repository ownership, branch and exact head, a clean worktree, released runs, idle workspace threads and references from other unfinished tasks. A done task archives with any idle, errored or closed extra threads and records their IDs; a thread with an active turn or pending permission waits. Uncommitted files, unexpected or unpublished commits, and changed Git ownership still preserve the workspace. Cancelled-task and in-flight archive paths still refuse an unrelated thread. An externally assigned coordinator's workspace is not owned by this task and is not archived by it. Archive intent is persisted; an uncertain outcome is inspected without blindly repeating the request.

An archive also proves Effigy runtime retirement (Effigy contract 005). The plugin captures the worktree's runtime scope token before the archive, persists it with the archive intent, and afterwards proves retirement with the idempotent `effigy container retire --scope <token> --yes`; exit 0 means nothing owned remains. A non-zero result, a timeout or a teardown Paseo reports as failed flags the task's cleanup as **runtime retirement failed** with the command's output tail and retries the same command with backoff until it succeeds; the durable token also survives a restart between archive and proof. Owner `retry_effect` clears the backoff and retries immediately. A worktree Effigy never scoped has no token and nothing to prove. A retirement failure never reverses the archive or counts as a clean archive.

If a workspace disappears after merge but before closeout, the plugin can create a dedicated closeout worktree pinned to synchronized main and assign a new coordinator. Existing merge evidence is preserved; it does not merge again. An available explicitly assigned coordinator or a received closeout result takes precedence over recovery. Unknown agent-creation outcomes stay fenced; the known Paseo SDK missing-directory preflight error can be recovered once an exhaustive run lookup confirms no agent was created.


## History retention

Once daily while unpaused, the plugin purges task history 4 days after completion (Tom, 2026-10-20; previously 14), cancellation or explicit removal. Active and blocked tasks remain. Unreleased runs, pending/intent/uncertain notices, uncertain merge/archive operations and unfinished workspace cleanup defer purging. Pausing also pauses retention.

Purging removes bulky task records, events, runs, callback receipts and associated credentials/private tickets. A compact task ID, submission identity and final status remain: dependencies still resolve and repeated submissions cannot launch purged work again. Purged prerequisites appear as “history purged” without a detail link. Outcome rows are permanent: `queue.outcome` and `node bin/queue-cli.mjs outcome` read them by task id or submission id after the live task is gone. `outcome-search` queries the same rows by repository, text, lane, date, commit or PR (Spec 025); its indexed columns and FTS5 projection are written with the row and rebuildable from it. The `lane` filter matches any of a row's `lanes` through one index row per task and lane. SQLite reuses the freed pages; its file need not shrink immediately.

## Coordinator-first recovery

Attention, blocked and error results go to the job coordinator before the originating planning thread. The plugin reuses an idle assigned coordinator, or creates one in the job workspace from the coordinator pool. Busy threads are left alone. Recovery respects project/global capacity, pause/drain and existing workspace leases.

The coordinator gets one bounded diagnosis: inspect the issue, ask the affected thread to finish reporting within its existing authority, or resolve the stop directly through one owner verb. The coordinator reports with `nucleus_report` (`status: recovered`, `escalate`, `blocked` or `error`) and may return one typed `coordinatorAction` — `restart`, `route`, `move` or `cannot` — naming the stop it resolved; Nucleus checks the action against the task's current stop, applies it through the shared owner-verb registry with one `owner_control` event, records the outcome, and does not start another coordinator run for the same stop. The summary supplies context, never phase or side-effect proof; a stale coordinator report cannot block or overwrite an accepted result. The earlier narrow `recoveryAction` reports (`reconcile`, `retry`, `revise`, `resume_worker`, `reassign_origin`) were deleted on 2026-10-14 (Spec 050 step 4); historical reports stay readable, and a pending legacy action on a released run is recorded as not applied with its escalation kept. A PR branch mismatch still enters revision before mutation so identity-repair authority is durable. If GitHub was already repaired out of sequence, an explicit `move` can reconcile a different PR only when strict canonical branch, base, clean local worktree and exact remote-head verification passes and the original callback never established an accepted PR. It takes only the PR number and refuses a `reason` field: its authority is the verified identity, not a recorded explanation. `status: escalate` supplies the unresolved blocker and exact operator decision needed. Recovery cannot approve a PR, bypass merge checks, broaden the handoff or renew one-shot execution authority.

A coordinator that still owes closeout gets a reporting reminder on its existing run; its callback binding is preserved. Other recovery assignments have separate run IDs and durable, generation-fenced callbacks. Task details show recovery status and history.

The origin receives an attention notice only after explicit escalation, failed/unavailable coordinator recovery, uncertain delivery, or recurrence of the same issue after recovery. Three bounded recovery attempts per stage prevent loops across changing errors. Post-merge closeout receives a fresh budget independent of implementation recovery. Escalations are deduplicated; obsolete pending notices are suppressed. Completion recipients never receive these attention messages.

Weight is a per-model share, edited in the profile editor's Advanced disclosure with a 1–10 stepper: weight 2 receives roughly twice the assignments of weight 1 across the whole eligible pool, whatever subscription group each model sits in. A profile save preserves its own weight rather than inheriting the subscription group's, and existing stored values keep working as each entry's own weight with no migration. Cost is optional per-profile metadata: very low, low, medium, high or very high. Existing profiles remain unset until classified; selecting an active cost again clears it. Cost is displayed for decisions, but does not change automatic dispatch scoring. The capability level is a second optional five-level rating beside cost using the same values; it does not change eligibility either.

Profile autosaves serialize writes and retain the latest pending edit. Editors remain open after saves; failures are shown explicitly. Closing an editor flushes pending valid group text. Empty group names are not saved.

## Origin routing

The plugin records the originating workspace at submission, and backfills it for older tasks while their original threads still exist. Automatic Chatterbox discovery was retired with project ownership (Spec 058 cutover 5, 2026-11-02): when the current notification thread is deleted or archived, Nucleus records a missing-origin error and waits — it no longer searches the workspace for a replacement or reassigns the planning recipient automatically.

A missing origin is planning-owned: a recovery coordinator may report a defensible successor with its evidence, and the operator at the board or the task's owner disposes of it with `queue.reparent` (`bin/nucleus-reparent.mjs`). For legacy tasks whose workspace was never recorded and whose original thread is already gone, the successor must be established from evidence; a same-named agent elsewhere is never chosen on its name alone.

The original submitting thread remains immutable; the current notification recipient and reassignment history are separate. Pending notices follow a reparent, delivered notices are not replayed, and uncertain deliveries remain fenced. Transport failures never trigger reassignment. Pause defers the origin pass. Unresolved routing remains visible in Open/Attention, including completed tasks awaiting notification; workspace cleanup waits while recovery is outstanding.

Notification details distinguish an unsent notice waiting for an idle/ready recipient from uncertain delivery. Routine closeout notices wait for idle. Pause/drain defers both. Accepted notifications retain their message IDs and are not repeated.

## Review entry for external PRs

Bring a finished external PR onto the board through [review entry](skills/nucleus/references/review-entry.md). The task receives an independent reviewer and follows the normal exact-head review, verification, merge and closeout gates. Existing worker threads cannot be registered as queue workers; workers can register themselves from their own worktree with `task.register`.

Review publication accepts markerless findings or exactly one marker matching the retained task, reviewer run, head and verdict. It preserves matching marked findings without rewriting the accepted callback. Foreign or duplicate markers are rejected before new callbacks are accepted. For an older accepted review held by the former blanket marker rejection, inspect the retained run and use `queue.task` with current version, `action:"restart"` and a `reason` after upgrading. Existing exact-head, independent-review, publication reconciliation and merge gates still apply; no replacement reviewer or direct database edit is needed for this format-only case.


## Frontier profile gate

A profile's capability runs `low` to `frontier`. Automatic eligibility is capability tier × usage level, cost × usage level and On/Off. A `frontier` profile is excluded from automatic worker, reviewer, coordinator and replacement selection below the Maximum usage level, and a profile above the level's cost ceiling (at Normal, very_high cost) is excluded too. The host-wide usage level (Settings → Dispatch limits, or `queue.usage`; Spec 052) moves those lines: High allows every cost, Maximum also brings frontier profiles into automatic selection, while Low and Minimal hold it to cheaper profiles. A submission can opt in per role with `profileRequests.worker` (or `.reviewer` / `.coordinator`): `{profileId, reason, required}`. Requests honor all existing availability, role, scope and review independence gates; `required:false` permits automatic-pool fallback, while `true` waits. Worker authorization never leaks to other roles. Cost remains descriptive and does not change weighting.

Before worker dispatch, `queue.task` `set_routing` changes any named routing fields on the current task version: `scope`, `complexity`, `preferredProfileId`, `requirePreferred`, `thinkingOptionId`, and `profileRequests`. The pre-rename `capability` key is refused with a message naming `scope`. Editing complexity affects future selection only; a running worker or reviewer is never replaced and accepted reviews are untouched. Use `null` for a role request to clear it. It requires `reason`; the CLI also requires `note` naming the operator authorization and records it as relayed. The board action is recorded as the operator's own. The control keeps task number, dependencies, lanes and brief identity. After worker intent or agent creation, use `route` with `role: worker` and a `profileId` to choose the replacement's profile, then `restart` with `fresh: true`. Nucleus rechecks that profile when the replacement actually starts. An unavailable subscription group may be named in a routing change; the event warns, and dispatch waits for an eligible profile. Spec 050 adds `route` — a role, a profile and a required reason in any unfinished phase — which supersedes these narrow controls for a role's profile, lifts a matching worker exclusion, and with `now` stops and replaces the role's live run.

To record that a worker must get no further turns on a live, unmerged task, use the current task version with `action: "exclude_worker"`, `workerExclusion: {agentId: "…"}` or `{profileId: "…"}`, and a required `reason`. A relayed CLI decision also names its authority in `note`. Task detail and recovery coordinator prompts show the exclusion. Nucleus refuses to resume an excluded retained worker; a changes-requested revision routes through worker replacement, and excluded profiles are omitted from candidate selection. An agent exclusion applies to that exact agent; a profile exclusion applies to every agent using that profile for this task. The coordination panel offers both controls for the current worker.

Profile rows show their group's active availability limit and reset date, and indicate Unavailable even when the profile itself is enabled. Selection mode saves automatically alongside other profile settings.

## Project development

Canonical planning starts at [docs/README.md](docs/README.md). Use `effigy setup`, `effigy check`, `effigy test --plan`, `effigy qa:docs` and `effigy qa` from this checkout. The installed plugin ID is `nucleus`; reload only that plugin after validation.

`effigy qa` runs the parallel suite six files at a time, then `test:timing`, which runs the wall-clock oracles (tests declared with `timingTest` from `test/support/timing.ts`) one at a time and reruns a failure once. A failure while the host's 1-minute load average is above its core count is reported as inconclusive and does not fail QA, since it cannot separate a regression from host load; `QUEUE_TIMING_STRICT=1` makes it fail. Test hooks expected to finish use `HOOK_TEST_TIMEOUT_MS` from `test/support/budgets.ts`. On macOS the first launch of each new executable is scanned, and the suite creates hundreds of hook scripts and checkouts, so more parallel files make hooks overrun rather than finish sooner. A new wall-clock assertion belongs in `timingTest`; a new hook that should finish uses the shared budget.

Both lanes keep their console reporter on stdout and end with a `qa-durations` table on stderr: the lane's total wall time and each file's wall time, slowest first, failures marked. A milestone QA run's stderr log keeps the whole table while its stdout log is capped, so `project.qa` artifacts show where the time went.
